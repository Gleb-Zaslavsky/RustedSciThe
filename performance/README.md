# Performance Regression Gates

Status: Windows Debug contract suite passes; targeted Windows Release baseline
comparisons have passed for selected workloads, 2026-10-21. The registry
contains 196 scenarios, including full supported-route matrices for Radau (24
cells), BDF (8 cells), LSODE2 (30 cells), BVP_Damp (66 cells), BVP_sci (30
cells), BE (4 cells), Nonlinear_systems (6 cells), optimisation (14 cells),
plus standalone and large-workload scenarios. The previous Windows calibration
had local baseline files for 100 active scenario IDs. The former BDF/LSODE2
IDs were superseded by longer workload contracts; all 8 BDF and 30 LSODE2
replacement baselines are now recorded, and both full matrices passed Release
comparison on 2026-10-21. Robertson micro-solves are no longer registered.
Earlier clean-source recording passed most other selected groups.
All six nonlinear and fourteen optimisation workloads passed targeted Release
comparisons; several other solver families and large BVP workloads also passed
comparisons. Baselines are local and Git-ignored, not a portable shared
reference. The runner is not yet a complete release-quality regression gate.
See [TODO.md](TODO.md) for validation and coverage gaps.

This repository tool will detect performance changes in selected, fixed
RustedSciThe workloads on the same registered machine. It complements numerical
correctness and algorithmic parity checks. It does not replace their verdicts.

## Ownership

| Artifact | Purpose | Update policy |
| --- | --- | --- |
| Existing solver STORY_TESTS Markdown | Research history, interpretation, engineering decisions | Developer edits |
| Existing `test_reports/` | Experimental matrices and stage diagnostics | Existing tests and scripts |
| `performance/machines/` | Local machine profiles tied to an installation ID | Generated by registration; Git-ignored |
| `performance/baselines/` | Local machine/environment/scenario references | Generated by `record`; Git-ignored, overwrite requires `--force` |
| `performance/runs/` | Individual gate reports and raw measurements | Runner output, Git-ignored |
| `performance/local/` | Optional local working artifacts | Git-ignored |

The local machine UUID belongs in the OS user configuration directory, outside
the checkout. Do not put usernames, absolute personal paths or hardware serial
numbers into versioned profiles.

## Runner and Isolation

Use one explicitly declared, opt-in Cargo binary named `perf-gates` in the
existing package, with its source under `performance/runner/`. No new workspace
crate is needed. Keep CLI, registry/workloads, environment, measurement,
comparison/storage and reporting in a few cohesive private modules.

Neither the library module tree nor numerical APIs depend on these modules.
Existing benchmarks and STORY tests keep their independent entry points.
Reuse public workload definitions and solver APIs; extract small fixture
builders only when needed and after checking existing test semantics.

The required profiling axes are kept orthogonal: symbolic frontend
(`ExprLegacy`/`AtomView`), execution (`Lambdify`/`AOT` where implemented),
linear algebra layout (`Dense`/`Sparse`/`Banded` where implemented),
dispatch (`Sequential`/`Parallel` where implemented), and timing scope. A
scenario is a supported route, not a synthetic Cartesian-product cell: the
registry must not advertise combinations the solver does not implement.
Matched frontend or policy comparisons use identical equations, dimensions,
layout, tolerances, and lifecycle except for the named axis.

The current registry reuses shared IVP equation fixtures and public APIs for
BDF/LSODE2/Radau, BE benchmark
support, a nonlinear workload from the Criterion matrix, BVP_sci full-solve
routes, and one faithful compact banded solve. Its current matched
ExprLegacy/AtomView pairs cover BDF, Radau, LSODE2, BVP_Damp, BVP_sci, and BE. BDF additionally has a fixed
256-state diffusion matrix covering both frontends with Lambdify
Sequential/Parallel and AOT Whole/Parallel2. BDF uses its fixed Dense
implementation and does not expose a selectable layout axis. AOT uses a
runner-owned BuildIfMissing cache, `tcc`, and warmups. Radau additionally has a
complete fixed-workload matrix for the supported combinations:
ExprLegacy/AtomView x Lambdify/AOT x Dense/Sparse/Banded x
Sequential/Parallel. Its AOT route uses a runner-owned BuildIfMissing cache,
requires `tcc` on PATH, and uses at least one warmup to keep cold compilation
out of measured warm samples. LSODE2 has a fixed 256-state diffusion matrix for
ExprLegacy/AtomView x Dense/Sparse/Banded x Lambdify Sequential/Parallel/Auto
and AOT Whole/Parallel2, integrating to `t=0.05` with `max_step=0.001`. It
fixes LSODE2 to its BDF-only faithful controller
so the matrix isolates frontend, execution, layout, and callback policy rather
than mixing controller changes. Tiny Robertson cases remain correctness
coverage in the solver suites, not performance-registry gates.

For BVP_Damp, 44 Damped cells cover the existing oscillator and nonlinear
dashboard workloads across both frontends, all three layouts and Lambdify
Sequential/Parallel/Auto plus supported Sparse/Banded AOT Auto. Frozen adds 22
cells on the exact linear fixture already used by its Rust correctness tests;
it has a distinct boundary-condition contract from Damped. AOT continuation
re-prepares after each numeric parameter rebind because the current prepared
AOT runtime invalidates on rebind; `continuation_prepare_ms` makes that cost
explicit. Dense AOT is intentionally absent. `list` reports workload,
frontend, execution route, linear algebra layout, dispatch policy and telemetry
contract for every registered scenario. The representative nonlinear matrix
is described below; broader method-specific matrices and remaining optimization
routes remain explicit gaps in TODO, not implied coverage.

BVP_sci adds 30 scalar exponential full-solve cells: ExprLegacy/AtomViewNative
x Dense/Sparse/Banded, with Lambdify Sequential/Parallel/Auto and AOT
Sequential/Parallel. Every route checks exact-solution error, success status,
Off-versus-Detailed parity, and actual AOT selection where requested. The
scalar Banded route uses `(0,0)` bandwidth; block bandwidth belongs to larger
systems. The optional SuperLU bridge is deliberately excluded from this
portable matrix so Sparse measures StandardFaer.

The `bvp-large` group uses established combustion workloads rather than
millisecond-scale toy problems: BVP_sci uses its six-state combustion equations
on 1000 nodes with Sparse/Faer across ExprLegacy/AtomView and Lambdify/AOT;
BVP_Damp uses its six-state chemical combustion-3000 fixture across a curated
Sparse/Banded frontend and execution set. The two solvers use different
equations and are not a cross-solver parity pair. Each timed sample runs with
telemetry Off; a separate Detailed execution captures stage timings and checks
counter and solution parity. These workloads have their own IDs and baselines,
leaving the compact route matrices intact.

For stage-level performance baselines, prefer a complete solve taking at least
tens of milliseconds and, where practical, hundreds of milliseconds or longer.
Several-millisecond toy solves remain useful for fast correctness matrices but
are too sensitive to scheduler and timer noise to anchor performance baselines.
Detailed stage measurements are diagnostic and must be collected separately
from the telemetry-Off gate samples.

BE adds four matched parameterized-combustion routes: ExprLegacy/AtomView x
Lambdify/AOT. Dense linear algebra and sequential execution are fixed properties
of this API, not missing matrix cells. Each route checks conservation,
nonnegative finite states, final time, Off-versus-Detailed trajectory parity,
and that the requested AOT runtime is actually selected. Separate cold AOT
preparation/build/link and warm callback timings are emitted only when native
telemetry reports those stages.

Nonlinear_systems adds six matched dense Newton routes on the same 512-variable
quadratic-chain system with a known root: both frontends use Lambdify
Sequential/Parallel, while AOT is represented once per frontend because its
generated route has no callback-dispatch option. The fixed Dense implementation
is not expanded into fictitious Sparse/Banded rows. Every route validates the
root, residual and Off-versus-Detailed parity; preparation and native solve
stages are reported from the Detailed diagnostic run.

Optimisation adds 14 symbolic fitting routes on one deterministic
20,001-observation exponential/sinusoidal dataset. Gavin covers ExprLegacy and
AtomView for its three damping-update policies; classic `FittingSolver` covers
both frontends with Lambdify Sequential/Parallel; VarPro is represented through
its native ExprLegacy/Sequential API; and UniversalFitting gets a separate
route for each of LM, Gavin, and VarPro. No AOT or unsupported VarPro frontend /
dispatch cells are fabricated. Each route checks recovered coefficients,
R-squared, and Off-versus-Detailed result parity. Detailed callback and linear
stages are included only where the native telemetry type reports them.
These larger suites can be selected independently with `--group nonlinear-large`
and `--group optimization-large` when recording or comparing baselines.

The primary wall-clock gate must use telemetry Off. Every telemetry-Off
warmup and gate sample is collected before instrumented diagnostics begin.
Metric records preserve whether a value came from the gate or a diagnostic
pass, plus a runner-local timing-scope label and optional parent scope. A
reported zero remains zero; a structurally absent stage remains absent.
Radau stage timings are
collected by a separate `Timings` solve; BDF and LSODE2 use `Detailed` to retain
both stage timings and discrete work counters. These instrumented diagnostics do
not affect the Off-mode wall-clock gate. Other solvers should follow this
pattern using `Timings` or `Detailed`, according to native support. Reports must retain both views
without claiming that instrumented wall time is the uninstrumented runtime.
Each registry entry explicitly names its regression-gate timing. Initially,
`scenario_wall_ms` is the gate; preparation, setup, factorization and solve-stage
timings are retained as diagnostics and do not independently trigger a
regression verdict. Gate IDs are part of the versioned baseline contract.
Further solver and symbolic scenarios are
incremental; the runner does not enumerate a full experimental cross-product.
Run artifacts are written only below the Git-ignored `performance/runs/` tree.
Existing `test_reports/` and solver STORY_TESTS remain independent and are not
read or modified by the runner.

## Commands

Use Release for every CLI command for a consistent machine fingerprint. The
`list` and `machine register` commands do not run numerical workloads, but
using the same profile avoids accidentally registering a Debug environment.

```text
cargo run --release --features perf-gates --bin perf-gates -- list
cargo run --release --features perf-gates --bin perf-gates -- machine register --name home
cargo run --release --features perf-gates --bin perf-gates -- list --solver bdf
cargo run --release --features perf-gates --bin perf-gates -- record --group bdf-matrix --machine home
cargo run --release --features perf-gates --bin perf-gates -- list --group bdf-matrix
cargo run --release --features perf-gates --bin perf-gates -- compare --group bdf-matrix --machine home
```

`record` and `compare` require an explicit selector. An unknown selector is an
error. `compare` never writes a baseline; missing, incompatible or unstable
measurements cannot become PASS.
`--all` selects every registered scenario and therefore requires a compatible
baseline for every one. The short BVP route matrices are currently correctness
coverage without accepted performance baselines; prefer a solver or workload
group selector for calibrated comparisons. `list` reports both baseline state
and AOT compiler availability. AOT record/compare refuses to start a scenario
when its configured `tcc` executable cannot be found on `PATH`.
Baseline recording and live comparison reject Debug binaries. Debug builds
remain appropriate for runner unit tests and correctness-only smoke checks.
`record` also refuses a dirty or unversioned source tree by default. Generated
files under `performance/baselines/` are excluded from this source-dirty check:
they are local measurement outputs, so a multi-solver baseline session does not
require a commit after each solver. Machine profiles under
`performance/machines/` are also local: each installation registers its own
random identity, and profiles/baselines are Git-ignored. Changes to runner code,
scenario definitions or other source inputs still require a clean tree. To
compare on another machine, register that machine and record its own baselines;
these machine-specific files are not a portable shared reference corpus.
`--allow-dirty-source` is an explicit diagnostic escape hatch; the
baseline records the revision, dirty flag and lockfile fingerprint, so that
such a reference is visibly non-clean rather than silently misrepresented.

### PowerShell Helpers (Windows)

The scripts in `scripts/` keep common commands consistent and print Cargo
output directly to the terminal. They do not redirect logs or modify
`test_reports/`. Run them from any working directory; each resolves the
repository root from its own path.

On a new Windows installation, register a local machine alias and inspect the
compiler and scenario inventory:

```powershell
.\scripts\perf_gates_register_machine.ps1 -Name windows-dev
```

To use a specific installed Rustup toolchain, pass its exact toolchain name.
The helper scopes `RUSTUP_TOOLCHAIN` to the command sequence, so both `rustc`
and `cargo` use the selected installation:

```powershell
.\scripts\perf_gates_register_machine.ps1 -Name windows-stable -Toolchain stable-x86_64-pc-windows-msvc
```

The generic runner performs one addressed record or compare. Exactly one of
`-Solver`, `-Group` or `-Scenario` is required. Defaults are 10 warmups, 101
measured runs and a maximum relative MAD of 5%; adjust counts for the workload,
not the stability threshold:

```powershell
.\scripts\perf_gates_run.ps1 -Action Record -Group radau-matrix -Machine windows-dev -Runs 201
.\scripts\perf_gates_run.ps1 -Action Compare -Group radau-matrix -Machine windows-dev -Runs 201
.\scripts\perf_gates_run.ps1 -Action Record -Group bdf-matrix -Machine windows-dev -Runs 301
.\scripts\perf_gates_run.ps1 -Action Record -Scenario radau_diff512_aot_atom_banded_seq -Machine windows-dev -Runs 201 -Force
```

`-Force` replaces an existing baseline only during `Record`; use it only when
replacement is intentional. `Record` requires a clean source tree by default.
`-AllowDirtySource` is an explicit local diagnostic escape hatch and should
not be used for shared references.

Do not use extra repetitions as a substitute for workload duration. The
2026-10-21 clean-source record exposed that the former BDF 64-state and LSODE2
128-state diffusion routes were too short for robust gates; Robertson
micro-solves were below useful wall-clock resolution. The registry now uses
BDF diffusion with 256 states and LSODE2 diffusion with 256 states over
`t=[0,0.05]`, retaining all supported route cells. Old IDs remain only as
inactive local baseline history. More samples improve the estimate of spread,
but do not remove scheduler noise from a tiny solve. Debug correctness passed;
the new BDF/LSODE2 baselines were recorded and all 38 routes passed full Release
comparison on 2026-10-21. A few initial whole-matrix instability reports
cleared on isolated confirmation and subsequent full comparisons; baselines
were not overwritten.

The first-tier helper runs only curated performance group(s) for one solver.
It intentionally does not use `--all` or include every short correctness-matrix
cell. Backward Euler runs both its matrix and larger diffusion-chain workload:

```powershell
.\scripts\perf_gates_first_tier.ps1 -Solver bdf -Action Record -Machine windows-dev -Runs 301
.\scripts\perf_gates_first_tier.ps1 -Solver bdf -Action Compare -Machine windows-dev -Runs 301
.\scripts\perf_gates_first_tier.ps1 -Solver bvp-sci -Action Record -Machine windows-dev -Runs 101
.\scripts\perf_gates_first_tier.ps1 -Solver optimisation -Action Compare -Machine windows-dev -Runs 101
```

Supported `-Solver` values are `bdf`, `radau`, `lsode2`, `be`, `bvp-sci`,
`bvp-damp`, `nonlinear-systems` and `optimisation`. The helper maps each to
its large or matched performance group; `be` runs both `be-matrix` and
`large-system`. Add `-Toolchain stable-x86_64-pc-windows-msvc` to select a
Rustup toolchain. Use `-Force` only with `-Action Record` to intentionally
replace existing baselines.

### IVP Symbolic Stabilization Helpers

The IVP campaign has three separate entry points so correctness, regression
gates and long story/benchmark evidence remain independently runnable. If the
local PowerShell policy blocks scripts, launch them through
`powershell.exe -ExecutionPolicy Bypass` as shown below.

Run the complete maintained IVP library-test matrix in Release, including
ignored SciPy parity stories, shared symbolic/AOT/codegen tests, workload
fixtures and solver/facade tests. This runs `cargo test --lib` filters only;
it does not run examples or `cargo bench`. The helper resolves
`.venv-gavin-win` by default, or accepts an explicit interpreter containing
NumPy and SciPy:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\ivp_symbolic_release_tests.ps1 `
  -PythonPath .\.venv-gavin-win\Scripts\python.exe
```

For a smaller tests-only Release pass over the four implicit solver families
(LSODE2, Backward Euler, Radau and BDF), including ignored tests:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\release_implicit_ivp_tests.ps1
```

Compare only the curated first-tier IVP performance groups. This does not run
all registered scenarios and does not modify baselines:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\ivp_perf_gates.ps1 `
  -Action Compare -Machine windows-dev -Warmups 20 -Runs 301
```

Each invocation now writes a checkpointed matrix under
`test_reports/IVP_perf_gates/<UTC-timestamp>-<pid>/`:

- `summary.md`: solver/action outcomes and a table for every reported scenario,
  including primary wall median/MAD, sample count, confirmation median/MAD,
  error reason and links to evidence.
- `summary.json` and `scenarios.csv`: machine-readable outcomes. `unstable`,
  `regression`, and `error` remain distinct; an unstable run is never a pass.
- `technical/*.log`: live console transcripts, including baseline/current
  comparisons, percentage changes and compiler or preflight errors.
- `reports/`: copies of the exact native run summaries and measurement
  Markdown/TOML files announced by that invocation, with stage timings,
  counters, raw samples, source revision and toolchain identity. Original
  `performance/runs/` reports remain available.

The matrix continues with the next solver after instability or failure and
returns nonzero only after all selected steps have been attempted. Checkpoints
are refreshed before and after each solver/action: `running`/`pending` means
the campaign is incomplete, including after an interruption. The live log
remains available while a long solver group is still executing. A launch
failure without a native report is an explicit step error, not an empty pass.
Reports use the runner's generated summary format; unrecognized or inconsistent
formats are errors rather than guessed successes. No Python installation is
required for this performance-only matrix.

For the explicitly approved baseline refresh, run one solver's record and
compare before proceeding to the next solver:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\ivp_perf_gates.ps1 `
  -Action RecordCompare -Machine windows-dev -Warmups 20 -Runs 301 -Force
```

Commit reviewed changes first: `Record` still requires clean source unless
`-AllowDirtySource` is explicitly supplied. If any scenario fails to record,
the same solver's compare is marked `blocked` to avoid comparing a mixture of
old and new baselines; other solvers continue. Stable records already written
by that solver remain written, as in the native runner. There is no automatic
retry or replacement of unstable measurements. `Compare` alone never replaces
baselines. Use `-Solvers radau,lsode2` when invoking the script from PowerShell
to restrict the matrix, `-ReportRoot` to choose its output parent, or `-PlanOnly`
to print the execution plan without creating files or launching Cargo.

The orchestration/reporting contracts can be checked in seconds with synthetic
child processes, without numerical runs or baseline writes:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\tests\ivp_perf_gates_tests.ps1
```

The overnight command runs correctness, perf comparison, and the existing
BDF/Radau/LSODE2/BE release matrices. It preserves terminal output and stores a
campaign summary plus technical transcripts under
`test_reports/IVP_symbolic_nightly/`. The solver matrix scripts continue to
own their compact Tabled reports. No STORY_TESTS document is rewritten.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\ivp_symbolic_nightly.ps1 `
  -Machine windows-dev -PythonPath .\.venv-gavin-win\Scripts\python.exe
```

Use `-RefreshBaselines` only on a clean, reviewed source revision after a green
nightly comparison. The orchestrator blocks the force-record stage if any
earlier step fails. After a successful force-record it immediately repeats the
IVP comparison; a failed record blocks that verification stage:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\ivp_symbolic_nightly.ps1 `
  -Machine windows-dev -PythonPath .\.venv-gavin-win\Scripts\python.exe `
  -RefreshBaselines
```

The same runner CLI can be invoked directly on Linux after registering that
host locally, for example:

```sh
cargo run --release --features perf-gates --bin perf-gates -- machine register --name linux-dev
cargo run --release --features perf-gates --bin perf-gates -- record --group radau-matrix --machine linux-dev --warmups 10 --runs 201 --max-relative-mad 0.05
cargo run --release --features perf-gates --bin perf-gates -- compare --group radau-matrix --machine linux-dev --warmups 10 --runs 201 --max-relative-mad 0.05
```

PowerShell helpers are convenience wrappers, not a platform abstraction; the
Rust CLI remains the source of truth for selection and baseline policy. Never
compare against a baseline from another machine or environment ID.

Machine registration creates a local installation identity under the user's
OS configuration directory and a small alias profile under
`performance/machines/`. The profile is ignored and must not be committed or
copied to another installation. Runtime
provenance records source revision, dirty-tree state, Cargo.lock content
fingerprint and `rustc --version` from `PATH`. This does not prove which
compiler built an already-existing executable. Compiler version and source
revision are reported but are not hard compatibility keys: changed code and
toolchains are exactly what later comparisons should measure. They must
nevertheless be recorded in reports so results can be interpreted.
Build-time compiler and artifact provenance remain explicit limitations, not
inferred facts.

An uninstrumented solve and an instrumented diagnostic solve have separate
measurement contracts. Preparation, callbacks, numerical solve and continuation
must retain their declared scopes. Baseline schema 3 persists metric phase and
scope metadata; schema changes are rejected rather than reinterpreted.
Baselines describe the actual frontend,
execution route, linear backend, telemetry mode and cache lifecycle.

[`METRIC_CONTRACTS.md`](METRIC_CONTRACTS.md) maps emitted diagnostic IDs to
native fields and records units, route applicability, known aggregation
boundaries and overlaps. Native parent/child scope metadata is persisted where
the solver exposes it; unknown reset semantics are called out rather than
inferred.

Metrics are declared by each scenario; the runner does not add a wrapper timer
that would accidentally include correctness checks. Metric names and units
must remain identical across samples. Timings retain raw samples plus
median/MAD/min/max; discrete counters retain raw samples plus median and range.
Counter changes are reported as algorithmic-work diagnostics, not silently
converted into timing failures. Correctness diagnostics are stored separately.

Setup, solve and full-solve scopes may overlap by design. For example,
`scenario_wall_ms` must not be added to nested setup and solve values. Failed
scenarios and partial matrix outcomes are summarized in `summary.md` and
`summary.toml` under the run directory, without touching `test_reports/` or
STORY_TESTS.

Before the symbolic refactor, complete the minimal runner and record reviewed
release baselines from an identified source revision. Debug builds suffice for
runner logic and numerical validation; performance evidence requires release.
