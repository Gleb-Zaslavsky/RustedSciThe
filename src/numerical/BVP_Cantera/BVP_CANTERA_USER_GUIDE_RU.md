# Руководство пользователя BVP_Cantera

`BVP_Cantera` решает краевую задачу на фиксированной равномерной сетке и
использует Newton core в стиле Cantera. Его нелинейный цикл независим от
BVP_Damp и BVP_sci. Пользовательский фасад находится в общем
[`BVP_api`](../BVP_api/BVP_API_GUIDE_RU.md); здесь описаны возможности и
границы именно этого маршрута.

## Численная область

Дискретизация строится по trapezoid-схеме на фиксированной сетке. Неизвестные,
заданные граничными условиями, исключаются из packed Newton state и
восстанавливаются при формировании профиля. В этом маршруте нет grid
refinement, pseudo-transient recovery или mesh restart. Имена фиксированных
входов выводятся из символьных уравнений; значения можно привязать и заменить
без повторной подготовки Lambdify/AOT callbacks и структурного шаблона
Якобиана. `solve_parameter_loop` выполняет упорядоченное продолжение по
фиксированным входам: первая точка использует исходное приближение, следующие
— последний успешный профиль. Ошибка точки сохраняется в типизированном
отчёте и не прерывает дальнейшие попытки. Результат содержит полные профили,
физическую сетку и частичную native telemetry. Примеры через facade:
`examples/bvp_api_cantera_combustion_continuation.rs` и
`examples/bvp_api_cantera_bratu_continuation.rs`.

Newton controls включают взвешенную RMS-норму поправки с масштабированием по
компонентам, fraction-to-boundary для bounds, фиксированное уменьшение damping
в `sqrt(2)` раз, возраст/reuse Якобиана и ограниченные Cantera-повторы его
обновления после исчерпания damping. Успешный результат публикуется только
после выполнения критерия поправки. Ошибка имеет typed-вариант и сохраняет
последнее принятое состояние/частичный report; отвергнутый trial не становится
успешным результатом.

Результаты Sparse и Banded дополнительно проверяются на конечность и backward
residual с использованием повторно используемой scratch-памяти solver-а.
Некорректный результат возвращается как typed `NonFiniteLinearSolution` или
`LinearResidualCheckFailed` с частичным solve report; такой шаг не принимается.
Dense сохраняет проверку сингулярности своего backend-а.

## Символьные и линейные маршруты

`CanteraExprBvpOptions` позволяет выбрать `ExprLegacy` или нативный `AtomView`,
а также Lambdify или AOT. Для AOT нужно явно передать
`SymbolicIvpGeneratedBackendConfig` через `with_aot_config`; ошибки подготовки
и исполнения сохраняют typed cause, не переключая маршрут молча на Lambdify.

Поддерживаются Dense, Sparse и `BandedAuto`. Sparse и Banded собирают глобальный
Якобиан непосредственно из координатного шаблона, не создавая плотную
глобальную матрицу. Ширина полос выводится из символьной структуры и не задаётся
пользователем. Dense предназначен для компактных систем и сравнений; для
больших задач следует использовать структурный backend, если структура это
позволяет.

## Диагностика

Логирование по умолчанию выключено (`SolverLogLevel::Off`) и использует общий
логгер крейта. Native telemetry по умолчанию Off; Counters не читает часы,
Timings собирает и counters, и длительности. Частичный report численной попытки
остаётся доступен в typed error. Телеметрия подготовки symbolic/AOT относится к
отдельному lifecycle и не суммируется с временами native solve.

Пример фасада: `examples/bvp_api_cantera.rs`. Матрица корректности и отчётов:
`scripts/bvp_cantera_release_matrix.ps1`; группа крупных performance-сценариев:
`scripts/bvp_cantera_perf_gates.ps1`.
